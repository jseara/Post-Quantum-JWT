# Sprint 3 results: comparison and recommendations

This document covers S3-03 ([PROGRESS.md](PROGRESS.md#s3-03--publish-the-end-to-end-and-mitigation-results)): it compares Sprint 3's end-to-end and mitigation results with Sprint 1's signing times and Sprint 2's size limits, and answers RQ4 with recommendations for which configuration and mitigation fit which deployment, and what each trades off. The full results are in [RESULTS.md](RESULTS.md) (Sprint 1, local signature benchmark), [TRANSPORT_RESULTS.md](TRANSPORT_RESULTS.md) (Sprint 2, transport size limits), [END_TO_END_RESULTS.md](END_TO_END_RESULTS.md) (S3-01, end-to-end latency and throughput), and [MITIGATION_RESULTS.md](MITIGATION_RESULTS.md) (S3-02, smaller claim sets, cookie splitting, and reference tokens). Every table below is generated from those runs' committed result files by [scripts/transport_report.py](../scripts/transport_report.py).

S3-03 recorded no new run. Every Sprint 3 run is from macOS over loopback: the clients, nginx, waitress, the application, and the reference store ran on one machine, so the network cost of a token is calculated with a model, not measured. Sprint 1 also has a WSL2 run, and Sprint 2's sweeps, whose boundaries the derived table uses, are from WSL2; no Sprint 3 command has been run on WSL2. Every token in these runs was signed with ephemeral experiment keys, not production credentials: each experiment key was generated in memory and discarded.

## Comparison tables

**Conventions.** Sizes are in bytes, times in milliseconds, and throughput in verified requests per second; p95 is nearest-rank, as in Sprint 1. Each difference is the configuration's or the mitigation's mean minus its baseline's mean, so negative = faster; in the network table, a positive value means more upload time. Chromium coarsens its timer to about 0.1 ms, so its medians and p95 values are multiples of 0.1 ms; its means are not. A difference is attributed to a configuration or a mitigation only when it is larger than the same-size noise level, the difference between ES256's and EdDSA's means (their tokens are the same size), which is reported in [END_TO_END_RESULTS.md](END_TO_END_RESULTS.md#token-size-versus-verification) and in each mitigation's Latency section of [MITIGATION_RESULTS.md](MITIGATION_RESULTS.md#latency). **Measured** values were recorded by a committed run. **Derived** values compare a measured token size with a limit measured elsewhere (Sprint 2's WSL2 boundaries, or WSL2's 4 KiB `proxy_buffer_size`) without sending that token. **Calculated** values come from a model (the network model) and were not measured.

## Recommendations

These recommendations answer transport questions 4 and 5 in [RESULTS.md](RESULTS.md#questions-for-transport-testing) and questions 1–4 in [TRANSPORT_RESULTS.md](TRANSPORT_RESULTS.md#questions-for-sprint-3). End to end, over loopback, a larger token costs little: with S3-01's minimal-claims tokens, ML-DSA-44's request takes +0.029 ms over ES256's and SLH-DSA-SHA2-128f's +0.496 ms (http.client, concurrency 1; [load.json](load/20261117T035444Z-macos/load.json) `comparisons`), but on a real uplink the calculated transfer cost outweighs the measured verification cost for every post-quantum configuration. Of the mitigations, smaller claim sets bring only ML-DSA-44's cookie within the documented default limits; cookie splitting gets every token under Chromium's per-cookie limit but SLH-DSA through nginx only with raised buffers; and reference tokens get every configuration through every limit, at the price of stateless and offline verification and of a lookup on every request: 0.001 ms in the application's memory and 0.125–0.178 ms from a separate store process over loopback (http.client, concurrency 1; [refs.json](refs/20261119T051144Z-macos/refs.json) `latency.rows`). HTTPS and HTTP/2 (question 5 in TRANSPORT_RESULTS.md) are S3-04's work and are not answered here.

## Reproduce

The comparison tables are generated, so this document can be checked against the committed results from a clean checkout. With the environment from [TRANSPORT.md](TRANSPORT.md#setup) and `TRANSPORT_ENV` set, from the repository root:

```bash
# exit 0 if the generated block matches the committed results, 1 if it is out of date:
"$TRANSPORT_ENV/bin/python" scripts/transport_report.py --check
# replace the block between the two marker lines, leaving the rest of this file unchanged:
"$TRANSPORT_ENV/bin/python" scripts/transport_report.py --write
# print the generated block:
"$TRANSPORT_ENV/bin/python" scripts/transport_report.py
```

The script reads only the committed files listed in its `SOURCES`, the JSON summaries in the Sources table, with the standard library, so it needs no stack, browser, or network, and it gives the same output from any working directory. It does not recompute the summaries from `raw.csv` or `raw.csv.gz`; the result documents describe how each summary can be recomputed from them.

The underlying runs are recorded again with `make load` ([END_TO_END_RESULTS.md](END_TO_END_RESULTS.md#reproduce)) and with `make claims`, `make cookies`, and `make refs` ([smaller claim sets](MITIGATION_RESULTS.md#reproduce), [cookie splitting](MITIGATION_RESULTS.md#reproduce-1), and [reference tokens](MITIGATION_RESULTS.md#reproduce-2) in MITIGATION_RESULTS.md); each writes a new run directory under `results/`. Sprint 1's benchmark and Sprint 2's sweeps are reproduced as [RESULTS.md](RESULTS.md#reproduce) and [TRANSPORT_RESULTS.md](TRANSPORT_RESULTS.md#reproduce) describe. Pointing the tables at new runs means editing `SOURCES` in [scripts/transport_report.py](../scripts/transport_report.py) and running `--write`; the Recommendations section is written by hand, so its figures then have to be checked against the new tables.

## Limitations

- **Sprint 3 not run on WSL2.** The `load`, `claims`, `cookies`, and `refs` commands have not been run on WSL2, so every Sprint 3 measurement is from macOS; the WSL2 figures in this document are Sprint 1's measurements and values derived from Sprint 2's WSL2 sweeps, not Sprint 3 measurements. Recommendations specific to WSL2 need those runs first.
- **Loopback only.** Every Sprint 3 latency was measured over loopback on one machine, so no real network was measured: the network cost is calculated from a model with illustrative profiles, and a remote reference store across a real network would add its own round trip per request.
- **HTTP/1.1 without TLS.** The mitigations were not measured over HTTPS or HTTP/2. S3-04 repeated only Sprint 2's size sweeps over them ([TRANSPORT_RESULTS.md](TRANSPORT_RESULTS.md#https-and-http2-s3-04)), where TLS moved no boundary and HPACK let Chromium's Bearer tokens further past nginx's default header limit. Over HTTP/2 a browser may also send each cookie as its own header field, which could change cookie splitting's limits.
- **Chromium only.** Firefox and Safari have their own per-cookie and per-domain limits, which were not measured.
- **One run each.** Each run was recorded once, so run-to-run variation was not measured. The same-size noise level is measured within one run only, and each mitigation's runs ran in a fixed order, so a drift between them cannot be told apart from a small difference; the concurrency 4 and Chromium differences are shown but not attributed.
- **Experiment keys and stores.** Every token was signed with an ephemeral experiment key, not a production credential. The reference stores are experiment stores that keep everything in memory, not a production store such as Redis, and trusting or caching verified tokens in the store was not measured.
- **Not the default limits for latency.** Every Sprint 3 latency stack raised nginx's header buffers to 32k and used the non-default `--upstream-keepalive 64`, and the cookie-splitting latency stacks also raised `--proxy-buffers 32k`; the size-limit tables say which limits each verdict used.
- **Fixtures and what was left out.** The OIDC and essential claim sets are fixtures with illustrative values; a real provider's claims could be larger or smaller. Fetching dropped claims and cleaning up stale chunks were not measured.
